# BLS oracle corpus provenance

Every output, verdict and decode outcome in these files is what Dash Core's own
BLS code returned through the consensus oracle's `oracle_bls_exec` (ABI 14). The
inputs are generated by `contrib/vectors/bls_oracle` (see its README.md).

## Oracle

- Dash Core commit `0dd12af0644b5b3aafc8d60cb2a786292d7788b0` (branch `node/bs12-oracle-bls-v24.0`, the program's v24.0
  pin): v24.0.0-rc.3 plus the test-only consensus oracle shim. `src/bls/` and `src/dashbls/` are unchanged from
  v24.0.0-rc.3.
- Archive `libdash_oracle_v24_0.a` sha256 `3af88a4b55009c08797ab79952f1c18d39264e94eeccde1607ca1ca9ac5ee18d`, built
  reproducibly by rust-dashcore's `contrib/node/build-oracle.sh` (plain flavour; `check-oracle-repro.sh` found it
  byte-identical in two cache roots).
- Probe: `contrib/vectors/bls_oracle/build.sh <archive> <probe>`.

## relic.json5

- Content: relic's arithmetic on points outside the subgroup through the reference implementation's BLS wrappers under
  the legacy scheme (the BS11a design's probes P1 to P5 and its fixed vectors, rust-dashcore
  `docs/node-program/designs/BS11a-legacy-bls.md` §2.2 and §8): each step's status, relic's error code after it and the
  relic calls it made, read through `oracle_bls_exec` at ABI 19 (element operations, the code field and the call log).
- Observed and inferred: the rows observe P2 (`[k](0, 2)` gives (0, 0)), P3 (no code on off-curve addition and
  multiplication) and P5 (an off-curve signature's verify is rejected, with its pairing calls logged). P1
  (`fp_inv(0) = 0`) and P4 (`FE(0) = 0`) are wrapper consequences of those rows: no oracle op exposes `fp_inv` or
  `pp_exp_k12`. The design's raw relic probe (`relic_probe.cpp`, sha256
  `cce9099290653459dcd2a252f68b970950b477e56bd58b5ad95867516e56d2d4`, linked against the reference implementation's own
  `librelic` and `libdashbls`, whose relic is the same at v23.1.8 and v24.0.0-rc.3) printed `inv0` as 48 zero bytes with
  code 0, and `FE(0) is zero=1 is one=0` with code 0.
- Scope: these rows seed the relic engine's element operations (G1 and G2 off-subgroup addition, negation and
  multiplication, the infinity shapes, and the legacy and basic verify). Aggregation, threshold and DH coverage for
  BS11b comes from the design's later differential scripts, not from these rows.
- Call logs: the reference implementation's BLS library reads two curve constants once per process, so the process's
  first legacy hash to G2 logs two more `bn_make`, `bn_read_str` pairs. The generator signs once under the legacy
  scheme before the rows, and a log is comparable only with one from a process warmed the same way; codes and outputs
  do not depend on it.
- Oracle: reference implementation commit `88c3e58dc292a1a45bd02eb03c653325d08a531b` (branch
  `node/bs11a-2-oracle-bls-v24.0`): the pin above with the oracle shim at ABI 19; `src/bls/` and `src/dashbls/` are
  unchanged from v24.0.0-rc.3. Archive `libdash_oracle_v24_0.a` sha256
  `ec49447f277aa7fe5c7b2ecda1dcbf0020e86bac74600c2a3ce6f0448873e9db`, built reproducibly by rust-dashcore's
  `contrib/node/build-oracle.sh` (plain flavour; `check-oracle-repro.sh` found it byte-identical in two cache roots).
- Generator: `gen.py --probe <probe> --out-dir pkgs/pkc/corpus/bls_oracle --only relic`, the probe linked against that
  archive.
- `relic.json5` sha256 `2edcf2e5e4dc29a7b761be9a70a073334a3831d0c4113f5fa8e8f16d28d99d29`

## arith.json5

- Content: the reference implementation's element operations over mixed registers in both groups (rust-dashcore
  `docs/node-program/designs/BS11a-legacy-bls.md` §8 seeds, BS11a-3 D17): every producer of the design's §3.1 shape
  table against an Exotic value, a zero-z engine result and an engine product (`IMPL_EQ`, `EQ`, `ADD` both ways,
  `ISVALID`) under both flags, and among themselves under the basic scheme; the scalar classes (the `mul_dig`
  boundary, r and its neighbours, 2^256 - 1, scalars at the GLV and GLS recodings' boundaries) on Usable and Exotic
  values; `AGG_PK`/`AGG_SIG` in span (empty, one, many) and pair form, the pair form's assertion included; `DH` over
  valid, invalid and Exotic sides with an `INPLACE` kept element; `SER` and `SER_HASH`'s cache under both flags. Each
  step has its status, relic's error code after it and its call log, read through `oracle_bls_exec` (ABI 26 ops and
  flags).
- Oracle: reference implementation commit `77dbec82427cfa91d420825235ca0f7abf5c984e` (branch
  `node/bl211-oracle-v24.0`, rust-dashcore's v24.0 pin, ABI 28); `src/bls/` and `src/dashbls/` are unchanged from
  v24.0.0-rc.3. Archive `libdash_oracle_v24_0.a` sha256
  `ceae0c8a05149c25e523a811f84f9b432dfa4f3c6b77bc7fcc4b3901e5daa519` (rust-dashcore `dash-oracle-sys/pins.txt`).
- Call logs: warmed as `relic.json5`'s.
- Generator: `gen.py --probe <probe> --out-dir pkgs/pkc/corpus/bls_oracle --only arith`, the probe linked against that
  archive. The same probe regenerates `relic.json5` byte for byte below its header line.
- `arith.json5` sha256 `2dacaf4bf00a5b36249c5904f72ee911efa1117d458a921750e7be11ce753c89`

## dkg.json5

- Content: a regtest DKG transcript; see below.
- Generator: `dkg.py --probe <probe> --run <run dir> --argv <argv log> --out dkg.json5`.
- Run: Core's `test/functional/feature_llmq_dkgerrors.py` from the v24.0.0-rc.3 tree (0364ed626e), PRNG seed
  5249215831811370464, against the release `dashd` 24.0.0-rc.3 (sha256
  `e204e3163185b1bffcd3bf3532c0957d8cc11019eaf8f3dbc3b2fc82a7ab5bb4`) run with `-capturemessages`. Core's members are
  random, so a new run gives a new transcript.
- Kept: the type-100 sessions' qcontrib, qcomplaint, qjustify, qpcommit, qfcommit and qsigrec messages, the members in
  Core's order (debug.log), the operators' regtest keys (the logged command lines), and every share, aggregate and
  verdict Core derives.
- `dkg.json5` sha256 `e5d2163fefe7090b7c5357d57ffd98396053b1459e0b42bf038e2f7731bdcaa2`
